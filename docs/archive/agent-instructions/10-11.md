TL;DR design

One dynamic route: /[sale] renders any sale from Sanity by slug. Two layout variants (“Standard” ≈ your SalePage, “Paikka” ≈ your PaikkaPage) chosen in content.

Sanity = the builder: you (or a tiny internal UI) create a Sale doc, attach Products, pick layout/theme, pickup window, email template, tracking, etc.

Square first, 3 levels
A. Checkout Links (fastest, safest) — per product, no cart.
B. Inline Checkout (Web Payments SDK) — simple cart; serverless Order+Payment.
C. Subscriptions / inventory — opt-in with Square APIs.

Webhooks mirror: Square → webhook → Supabase table for “orders” & live counts; update page tracker—no Firestore.

ISR + webhooks: on any Sanity change or order, revalidate the page.

Optional microfrontend: if main app deploys are flaky, you can auto-scaffold apps/sale-[slug] from a template and proxy /[slug] to it.

Square integration choices

Tier A: Checkout Links (recommended first)

Create one link per product/variation (CLI below). Store the URLs in the product doc. No PCI complexity; ultra-robust.

Tier B: Inline checkout

Use Web Payments SDK to tokenize; your API creates an Order + Payment (or Checkout) server-side with metadata { saleSlug, productId, customerEmail }.

Keep SAQ A by never touching raw PAN; Square token only.

Webhooks

Subscribe to payment.created, payment.updated, order.updated.

On success: upsert orders(sale_slug, product_id, qty, amount, square_payment_id) in Supabase; increment cached counters; call ISR revalidate for /[sale].
